# jira-analytics

Программное средство для аналитики задач проекта в JIRA. Подключается к серверу через REST API, загружает задачи и строит графики. По умолчанию анализируется проект Apache Kafka (`KAFKA`) на `https://issues.apache.org/jira`.

## Возможности

| № | График | Файл результата | Статус |
|---|--------|-----------------|--------|
| 1 | Гистограмма времени жизни закрытых задач | `01_open_time_histogram.png` | готово |
| 2 | Гистограммы времени в каждом статусе | `02_status_<статус>.png` | готово |
| 3 | Созданные и закрытые задачи по дням + накопительный итог | `03_created_vs_resolved.png` | готово |
| 4 | Топ-30 пользователей (исполнитель и репортер) | `04_top_users.png` | готово |
| 5 | Гистограмма залогированного времени | `05_logged_time_histogram.png` | готово |
| 6 | Количество задач по степени серьёзности | `06_priority.png` | готово |

## Требования

- Python 3.10 или новее
- Доступ в интернет к серверу JIRA

## Установка

```
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # Linux/macOS
pip install -r requirements.txt
```

## Конфигурация (`config.ini`)

| Секция | Параметр | Описание |
|--------|----------|----------|
| `jira` | `base_url` | адрес сервера JIRA |
| `jira` | `project` | ключ проекта (например, `KAFKA`) |
| `jira` | `worklog_project` | проект для графика 5 (если пусто, используется `project`) |
| `jira` | `page_size` | размер страницы при загрузке задач |
| `jira` | `retries` | число повторных попыток при сетевой ошибке |
| `jira` | `timeout` | таймаут запроса, секунды |
| `output` | `directory` | папка для графиков |
| `plots` | `bins` | число столбцов гистограмм |
| `plots` | `max_days` | ограничение оси X в днях (пусто = без ограничения) |
| `plots` | `top_users` | сколько пользователей показывать на графике 4 (по умолчанию 30) |

## Запуск

Из корня репозитория:

```
# Windows (cmd)
set PYTHONPATH=src
python -m jira_analytics.main --config config.ini

# Linux/macOS
PYTHONPATH=src python -m jira_analytics.main --config config.ini
```

Графики сохраняются в папку `output/`. Полная загрузка проекта с историей изменений занимает несколько минут.

## Принятые решения и правила расчёта

- **Закрытая задача**: у задачи заполнено поле `resolutiondate` (в JQL: `resolution IS NOT EMPTY`).
- **График 1**: время жизни = `resolutiondate - created`, в днях. Задачи, у которых дата закрытия раньше даты создания, пропускаются. Ось Y логарифмическая, так как распределение имеет очень длинный хвост.
- **График 2**: статусы берутся из `changelog` (поле `status`).
  - Начальный статус задачи равен `fromString` первого перехода.
  - Время между соседними переходами засчитывается статусу, в котором задача находилась.
  - Время в последнем статусе не учитывается: у него нет конца.
  - Если задача возвращалась в один и тот же статус (например, Reopened), время суммируется, и в гистограмму идёт одно значение на задачу.
  - Для каждого статуса строится отдельная гистограмма.
  - Из-за этого правила у терминальных статусов (Resolved, Closed) число значений намного меньше числа задач, побывавших в статусе: учитываются только задачи, которые из статуса выходили (например, Resolved -> Closed или Resolved -> Reopened). Соответствующий JQL для сверки: `status CHANGED FROM "Resolved"`.
- **График 3**: учитываются все задачи проекта, а не только закрытые (запрос без `changelog`, поэтому быстрый). Дата берётся из `created` и `resolutiondate`, дни считаются в UTC, дни без событий заполняются нулями, чтобы накопительные линии не прерывались. Верхняя часть графика показывает число задач за день, нижняя накопительный итог.
- **График 4**: используются все задачи проекта (те же данные, что для графика 3, с дополнительными полями `assignee` и `reporter`).
  - Пользователь определяется по `displayName`, если его нет, то по `name`.
  - Задачи без исполнителя в рейтинг не входят (их число пишется в лог). Если у задачи нет репортера, она не учитывается в столбике репортера.
  - Для каждого пользователя считаются два числа: задачи как исполнитель и задачи как репортер. Если человек и завёл задачу, и ведёт её, она учитывается в обоих столбиках.
  - Рейтинг сортируется по сумме двух чисел (при равенстве по имени), на график выводятся первые `top_users` пользователей. Самый активный пользователь расположен сверху.
- **График 5**: берутся закрытые задачи с `timespent > 0` (поле `timespent` в JIRA содержит суммарное залогированное время в секундах). Время переводится в часы. Ось Y логарифмическая.
  - В проекте KAFKA таких задач всего 7, поэтому для графика 5 используется другой проект Apache, ZooKeeper (параметр `worklog_project` в `config.ini`). Остальные графики строятся по проекту из параметра `project`. Чтобы построить график 5 по Kafka, достаточно оставить `worklog_project` пустым.
- **График 6**: используются все задачи проекта (те же данные, что для графиков 3 и 4, с дополнительным полем `priority`).
  - Степень серьёзности соответствует стандартному полю JIRA `priority` (Blocker, Critical, Major, Minor, Trivial).
  - На сервере Apache существует и отдельное пользовательское поле Severity (`customfield_12311031`). В проекте Kafka оно не заполнено ни у одной задачи (JQL `project = KAFKA AND cf[12311031] is not EMPTY` возвращает 0 задач), поэтому для графика выбрано стандартное поле `priority`, которое заполнено у всех задач проекта.
  - Стандартные уровни выводятся в порядке серьёзности, нестандартные (если встретятся) после них по убыванию количества.
  - Задачи без приоритета в график не входят, их число пишется в лог.
  - Над каждым столбцом подписано точное количество задач.

## Логирование и обработка ошибок

- Логи пишутся через модуль `logging` (уровень INFO): прогресс загрузки, число задач, пути к графикам.
- Сетевые ошибки обрабатываются повторными запросами с нарастающей паузой, после исчерпания попыток выбрасывается `JiraClientError`.
- Ошибки конфигурации приводят к `ConfigError` и коду возврата 1.
